# StockPilot

**StockPilot** — WMS-платформа для учёта остатков, резервирования, комплектации заказов и контроля складских операций. Проект создаётся по ТЗ **PV-WMS-01, редакция 1.0**. Заказчик в документе вымышленный: проект является портфолио-симуляцией, а не подтверждением коммерческого договора.

Базовый контур: каталог SKU/партий, многоскладская структура, приёмка с расхождениями, перемещения, атомарный резерв с TTL, задания отбора, согласование недоборов, отгрузки, возвраты, двухэтапная инвентаризация, RBAC, аудит, CSV и операционные показатели. ### Технологии

- API: Python 3.12, FastAPI, psycopg 3, OpenAPI 3.x.
- БД: PostgreSQL 16, SQL-миграция, append-only журнал движений и аудита.
- UI: React 18, Vite, адаптивный CSS, мобильное рабочее место кладовщика.
- Развёртывание: Docker Compose (db, migrate, api, worker, web), проверки GitHub Actions. Для существующих томов миграция 002 запускается отдельным one-shot сервисом migrate.

## Локальный запуск

Нужны Docker Desktop (Compose v2) и Git.

~~~bash
git clone https://github.com/Onmaynec/StockPilot.git
cd StockPilot
cp .env.example .env
~~~

В Windows PowerShell замените cp на: Copy-Item .env.example .env.

Проверьте в .env значения POSTGRES_PASSWORD, DATABASE_URL (пароль должен совпадать), JWT_SECRET и DEMO_PASSWORD. Пример .env содержит только настройки локальной разработки, не используйте их для общедоступного сервера.

~~~bash
docker compose up -d --build
docker compose exec api python -m app.seed
~~~

Интерфейс: **http://localhost:8080**.

Демо-учётные записи (общий пароль берётся из DEMO_PASSWORD):
- admin@stockpilot.local
- manager@stockpilot.local
- picker@stockpilot.local
- supervisor@stockpilot.local
- director@stockpilot.local

Генератор создаёт 3 склада, 12 000 SKU, 200 клиентов, 30 пользователей, партии и движения с датами за последние 90 дней. Повторный запуск не удваивает проведённые демодвижения.

### API

OpenAPI автоматически формируется FastAPI. По умолчанию API-порт закрыт внешнему доступу: через nginx проксируется только префикс /api/. Для просмотра Swagger в локальной среде временно опубликуйте порт 8000 сервиса api в Compose и откройте /docs.

Пример создания заказа после получения Bearer-токена в POST /api/v1/auth/login:

~~~http
POST /api/v1/orders
Authorization: Bearer <token>
Content-Type: application/json

{"customer":"ООО Пример","items":[{"productId":"<uuid>","warehouseId":"<uuid>","qty":1}]}
~~~

~~~http
POST /api/v1/orders/<orderId>/reserve
Authorization: Bearer <token>
Idempotency-Key: unique-request-01
Content-Type: application/json

{"ttlMinutes":60}
~~~

При недостаточном доступном остатке резервирование отклоняется (HTTP 409) вместе с текущим остатком. Повтор с тем же ключом и телом возвращает тот же результат без второй операции.

### Интерфейс

Разделы: обзор, остатки, SKU, приёмка, заказы, отбор, отгрузки, перемещения, инвентаризации, аудит и импорт CSV. При комплектации кладовщик сканирует код или вводит его вручную, после чего подтверждает фактическое количество. Камера требует поддержки BarcodeDetector и HTTPS/localhost. Черновики хранит браузер; проводка выполняется только сервером.

При CSV-импорте обязательны столбцы sku,name, дополнительно можно использовать unit,barcode,category,pick_policy. Все строки проверяются перед единым коммитом. Каталог и агрегированные остатки доступны для экспорта через кнопки в интерфейсе или через GET /api/v1/export/products.csv и GET /api/v1/export/stocks.csv. Журнал проводок с фильтрами по SKU, складу, партии и документу доступен через GET /api/v1/movements.

### Проверки и эксплуатация

Интеграционные тесты предназначены только для отдельной тестовой БД: они очищают таблицы. CI поднимает собственный PostgreSQL 16, применяет миграцию, запускает pytest, проверяет синтаксис Python и сборку интерфейса.

Worker проверяет TTL резервов раз в 15 секунд и записывает истечение только один раз. Transactional outbox хранит внешние события, а worker **эмулирует** интеграцию журналированием (поставщика ERP пока нет).

## Обновление с v0.1.0

Скачайте последний код. Не удаляйте существующий том PostgreSQL:

~~~bash
git pull origin main
docker compose up -d --build
docker compose ps
~~~

Сервис migrate последовательно применяет backend/migrations/002_sessions.sql и 003_inventory.sql (добавляет водораздел журнала для актов пересчёта). При первом запуске PostgreSQL читает 001 и 002, повторный запуск 002 безопасен. Новые JWT содержат версию сеанса; **после обновления пользователям потребуется заново войти**. Изменение пароля и «Выйти со всех устройств» инкрементируют версию: прежние JWT больше не принимаются.

## Браузерные E2E

В GitHub Actions отдельная job e2e поднимает Docker Compose с demo seed и проходит реальный сценарий: менеджер создаёт заказ, резервирует, кладовщик вводит код вручную и отгружает, менеджер видит финальный статус. Проверяются мобильный Chromium (375+ px) и Firefox на ПК, а также отрицательный тест прав роли кладовщика. Локально:

~~~bash
cd frontend
npm install
npx playwright install chromium firefox
npm run test:e2e
~~~

Не запускайте E2E на рабочей базе: тесты создают документы и изменяют остатки. Используйте локальное демонстрационное окружение с demo seed.

История релиза: [docs/RELEASE_0.2.0.md](docs/RELEASE_0.2.0.md).


### Обновление до v0.4.0 с существующей базы

**Внимание:** файл `.env` из v0.3.0 требует ручного изменения **до** `docker compose up`. Не удаляйте том PostgreSQL и не заменяйте весь `.env` примером.

1. Снимите проверенную резервную копию (подробности в [руководстве](docs/OPERATIONS.md)).
2. Добавьте в свой `.env` независимые `APP_DB_USER=stockpilot_app` и `APP_DB_PASSWORD` (новый уникальный секрет).
3. Поменяйте `DATABASE_URL` с учётной записи владельца схемы на **`stockpilot_app`** с тем же новым паролем. Если в пароле используются специальные символы URI, примените percent-encoding.
4. Добавьте `TRUSTED_PROXY_CIDRS` с точными адресами доверенных прокси вашей инсталляции. В простом Docker Compose приватная сеть обычно использует `172.16.0.0/12,10.0.0.0/8`; для production диапазоны следует сузить.
5. Выполните `git pull origin main` и `docker compose up -d --build`; миграционный контейнер создаст прикладную роль и права перед запуском API. Запустите `docker compose exec -T api python -m app.security_check`.

Если миграция отказывает, **не** возвращайте API полномочия владельца схемы ради запуска: проверьте настройки учётных данных и журналы `docker compose logs migrate`.

Проверки GitHub Actions используют отдельную owner-роль только для миграций/интеграционных тестов, а запущенные API и worker работают с ограниченной ролью. Публикация GitHub Release остаётся отдельным шагом владельца репозитория.


### Администрирование v0.5.0

Войдите как администратор и откройте **Администрирование** в боковом меню. Вкладка «Сотрудники» создаёт учётные записи, назначает их склады, блокирует и разблокирует доступ. Вкладка «Склады и ячейки» управляет топологией; «Партии товаров» привязывает партии к выбранному SKU. Введённые пароли не выводятся в таблицах. Все операции проверяются на сервере по роли пользователя.

При смене складских назначений и блокировке все действовавшие токены **этого сотрудника** немедленно отзываются; после восстановления доступа сотрудник должен войти снова. Администратор не может заблокировать собственную учётную запись.

Это обновление автоматически применяет миграцию `005_catalog_search.sql` для частичного поиска SKU/названий. На большом каталоге создание индексов лучше запланировать на окно низкой нагрузки. Для существующего развёртывания после резервного копирования выполните:

```bash
git pull origin main
docker compose up -d --build
docker compose exec -T api python -m app.security_check
```

`.env` должен быть обновлён по инструкции v0.4.0. Не используйте `docker compose down -v` на рабочей базе.

Скрипт `app.write_profile` **намеренно создаёт документы и проводки** и предназначен только для отдельной временной базы, наполненной `app.seed`; запуск на рабочей БД недопустим. ### Резервное копирование и проверка восстановления (v0.7.0)

По умолчанию служба ежедневного резервирования выключена. Перед запуском создайте отдельную директорию `backups/` и настройте права доступа, расписание и срок хранения (переменные `BACKUP_INTERVAL_SECONDS` и `BACKUP_RETENTION_DAYS` в `.env`). Включение:

```bash
mkdir -p backups && chmod 700 backups
# Для Linux задайте в .env BACKUP_UID/BACKUP_GID согласно id -u / id -g
docker compose --profile backup up -d backup
docker compose logs -f backup
```

Сервис немедленно создаёт первый архив, затем повторяет операцию каждые 24 часа; при ошибке повторяет через 300 секунд. Архивы хранятся **в папке `./backups` на хосте**, не в томе PostgreSQL, с ограниченными правами, `*.sha256` и сохранением минимум двух последних архивов. Для критических данных необходима отдельная зашифрованная внешняя копия и проверка политики хранения.

Изолированный пробный запуск восстановления (не останавливает работающий StockPilot):

```bash
STOCKPILOT_RECOVERY_DRILL=1 STOCKPILOT_RECOVERY_ISOLATED=1 \
  sh scripts/recovery_drill.sh backups/stockpilot-YYYYMMDDTHHMMSSZ-PID.dump
```

Подставьте имя настоящего созданного архива. Скрипт создаёт **собственный** Docker Compose project, восстанавливает дамп и проверяет API, worker и nginx, сравнивает контрольные суммы и автоматически удаляет только временный recovery-том. Полное описание, условия запуска и ограничения RTO: [docs/OPERATIONS.md](docs/OPERATIONS.md). Не используйте `docker compose down -v` на рабочей базе.


### v0.8.0 — рабочее место кладовщика

На экране **Задания отбора** кладовщик выбирает фильтр «Мои активные задания» и подтверждает отбор артикулом SKU или штрихкодом. При недоборе система запрашивает подтверждение и переводит задачу в `shortage_pending`; провести отгрузку нельзя, пока старший смены не согласует недобор. Если камера или BarcodeDetector недоступны, можно ввести код вручную. На смартфоне поля и кнопки увеличены для работы касанием.

Старший смены или администратор назначает активное задание из выпадающего списка сотрудников, прикреплённых к соответствующему складу. После выхода из учётной записи черновики ввода удаляются. Для безопасности старые черновики в постоянном `localStorage`, созданные предыдущими версиями, очищаются при открытии приложения.

Дополнительные API: `GET /api/v1/picks?assignedToMe=true` и `GET /api/v1/picks/assignees?warehouseId=<uuid>` (только admin/supervisor). Назначение и подтверждение по-прежнему проверяются сервером, доступ к чужому складу не передаётся клиенту.

Автоматические мобильные/десктопные браузерные тесты не заменяют ручную проверку физического смартфона; AT-12 остаётся открытым до такой проверки.
