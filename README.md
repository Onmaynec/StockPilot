# StockPilot

**StockPilot** — WMS-платформа для учёта остатков, резервирования, комплектации заказов и контроля складских операций. Проект создаётся по ТЗ **PV-WMS-01, редакция 1.0**. Заказчик в документе вымышленный: проект является портфолио-симуляцией, а не подтверждением коммерческого договора.

## Текущая версия: 0.1.0 — разработка MVP

Реализован основной серверный контур: каталог SKU/партий, многоскладская структура, приёмка с расхождениями, перемещения, атомарный резерв с TTL, задания отбора, согласование недоборов, отгрузки, возвраты, двухэтапная инвентаризация, RBAC, аудит, CSV и операционные показатели. Разработана адаптивная SPA/PWA.

**Наличие кода не равно завершению приёмки.** Целевые p95, нагрузка 60 пользователей, фактическое восстановление за 30 минут и E2E разных ролей ещё должны быть подтверждены измерениями. См. [приёмочные сценарии](docs/ACCEPTANCE.md) и [ограничения](docs/KNOWN_LIMITATIONS.md).

### Технологии

- API: Python 3.12, FastAPI, psycopg 3, OpenAPI 3.x.
- БД: PostgreSQL 16, SQL-миграция, append-only журнал движений и аудита.
- UI: React 18, Vite, адаптивный CSS, мобильное рабочее место кладовщика.
- Развёртывание: Docker Compose (db, api, worker, web), проверки GitHub Actions.

## Локальный запуск

Нужны Docker Desktop (Compose v2) и Git.

~~~bash
git clone https://github.com/Onmaynec/StockPilot.git
cd StockPilot
cp .env.example .env
~~~

В Windows PowerShell замените cp на: Copy-Item .env.example .env.

Проверьте в .env значения POSTGRES_PASSWORD, DATABASE_URL (пароль должен совпадать), JWT_SECRET и DEMO_PASSWORD. Пример .env содержит только настройки локальной разработки, не используйте их для общедоступного сервера.

~~~bash
docker compose up -d --build
docker compose exec api python -m app.seed
~~~

Интерфейс: **http://localhost:8080**.

Демо-учётные записи (общий пароль берётся из DEMO_PASSWORD):
- admin@stockpilot.local
- manager@stockpilot.local
- picker@stockpilot.local
- supervisor@stockpilot.local
- director@stockpilot.local

Генератор создаёт 3 склада, 12 000 SKU, 200 клиентов, 30 пользователей, партии и движения с датами за последние 90 дней. Повторный запуск не удваивает проведённые демодвижения.

### API

OpenAPI автоматически формируется FastAPI. По умолчанию API-порт закрыт внешнему доступу: через nginx проксируется только префикс /api/. Для просмотра Swagger в локальной среде временно опубликуйте порт 8000 сервиса api в Compose и откройте /docs.

Пример создания заказа после получения Bearer-токена в POST /api/v1/auth/login:

~~~http
POST /api/v1/orders
Authorization: Bearer <token>
Content-Type: application/json

{"customer":"ООО Пример","items":[{"productId":"<uuid>","warehouseId":"<uuid>","qty":1}]}
~~~

~~~http
POST /api/v1/orders/<orderId>/reserve
Authorization: Bearer <token>
Idempotency-Key: unique-request-01
Content-Type: application/json

{"ttlMinutes":60}
~~~

При недостаточном доступном остатке резервирование отклоняется (HTTP 409) вместе с текущим остатком. Повтор с тем же ключом и телом возвращает тот же результат без второй операции.

### Интерфейс

Разделы: обзор, остатки, SKU, приёмка, заказы, отбор, отгрузки, перемещения, инвентаризации, аудит и импорт CSV. При комплектации кладовщик сканирует код или вводит его вручную, после чего подтверждает фактическое количество. Камера требует поддержки BarcodeDetector и HTTPS/localhost. Черновики хранит браузер; проводка выполняется только сервером.

При CSV-импорте обязательны столбцы sku,name, дополнительно можно использовать unit,barcode,category,pick_policy. Все строки проверяются перед единым коммитом. Каталог и агрегированные остатки доступны для экспорта через кнопки в интерфейсе или через GET /api/v1/export/products.csv и GET /api/v1/export/stocks.csv. Журнал проводок с фильтрами по SKU, складу, партии и документу доступен через GET /api/v1/movements.

### Проверки и эксплуатация

Интеграционные тесты предназначены только для отдельной тестовой БД: они очищают таблицы. CI поднимает собственный PostgreSQL 16, применяет миграцию, запускает pytest, проверяет синтаксис Python и сборку интерфейса.

Worker проверяет TTL резервов раз в 15 секунд и записывает истечение только один раз. Transactional outbox хранит внешние события, а worker **эмулирует** интеграцию журналированием (поставщика ERP пока нет).
