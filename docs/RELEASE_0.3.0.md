# StockPilot v0.3.0 — Inventory Accuracy & Reliability

## Изменения

### Контроль остатков
- В интерфейсе старшего смены, администратора и руководителя появилась страница **«Контроль остатков»**. Сервер возвращает только отрицательные остатки и позиции, где резерв и блокировки превосходят физический товар. Неисправные данные не меняются автоматически.
- Новый API `GET /api/v1/stocks/anomalies` с проверкой разрешённых складов, максимум 200 строк за запрос.
- `GET /api/v1/inventory/{id}/variance` показывает незаполненные строки, число расхождений, суммарную разницу и признак устаревшего среза.
- В журнал инвентаризаций добавлен просмотр расхождений до утверждения.
- В схему добавлен `inventory_counts.snapshot_movement_id`, фиксирующий верхнюю границу проведённого журнала на момент создания акта. При утверждении система сравнивает её с последующими проводками, даже если их `created_at` задним числом раньше даты среза; отдельно учитываются новые комбинации товар/ячейка/партия.
- Старые акты со значением NULL сохраняют прежнюю проверку по времени. Миграция 003 повторно применима.

### Эксплуатационные проверки
- `scripts/verify_restore.sh`: полноценный `pg_dump -Fc`, реальный `pg_restore` во **временную БД**, сравнение количества сущностей, контрольных сумм упорядоченных журналов и агрегатов остатков. При ошибке операция не затрагивает рабочую БД; временная БД удаляется.
- `python -m app.load_profile`: 60 отдельных тестовых учётных записей, 10 авторизованных GET-запросов на пользователя, конкурентный запуск, измерение p50/p95/p99, ошибок и грубого показателя RSS API. Тестовые аккаунты удаляются после измерений. Запуск требует переменную `STOCKPILOT_PERF_ALLOW=1`.
- CI запускает оба сценария после наполнения демобазы (12 000 SKU) и сохраняет два JSON-отчёта артефактами workflow.

### Регрессии
- Проверка расхождений/задним числом созданного движения;
- Проверка контроля отрицательного остатка и ограничений ролей;
- Существующие тесты блокировок, резерва и сквозной Playwright продолжают выполняться.

## Статус ТЗ

AT-10: создан **воспроизводимый базовый профиль одновременного чтения** с 60 отдельными идентичностями. Это **не** полная проверка 350 заказов и 3000 движений в сутки; нагрузочные критерии для записи остаются открыты.

AT-11: добавлен автоматический реальный restore-тест и сравнение контрольных сумм на демонстрационном стенде; production-RTO менее 30 минут не подтверждён этим тестом. До закрытия Issue необходима сверка на отдельной инфраструктуре, замер полного восстановления сервиса и регламент бэкапов.

AT-12: браузерные E2E проверяются в CI, ручная приёмка на настоящем мобильном устройстве ещё не выполнена.

## Обновление

Выполните `git pull origin main` и `docker compose up -d --build`. Сервис `migrate` применит `002_sessions.sql` и `003_inventory.sql` без удаления тома. До обновления рабочей БД сделайте резервную копию.

Для локального повторения эксплуатационных проверок:
```bash
docker compose exec api python -m app.seed
STOCKPILOT_VERIFY_RESTORE=1 sh scripts/verify_restore.sh
docker compose exec -T -e STOCKPILOT_PERF_ALLOW=1 api python -m app.load_profile
```
Оба сценария предназначены **только для выделенного тестового стенда**. Не выполняйте нагрузочный сценарий в production.
