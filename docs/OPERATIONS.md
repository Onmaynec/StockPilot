# Эксплуатация и восстановление

## Резервное копирование

~~~bash
mkdir -p backups
bash scripts/backup.sh backups/stockpilot.dump
~~~

Используется pg_dump -Fc внутри контейнера PostgreSQL. Бэкапы могут содержать персональные данные, не добавляйте их в Git. В production нужны внешнее зашифрованное хранилище, ежедневное расписание и ротация.

## Восстановление

**Осторожно: заменяет данные в целевой БД!** Перед началом создайте дополнительную копию.

~~~bash
docker compose stop api worker
bash scripts/restore.sh backups/stockpilot.dump
docker compose up -d api worker
~~~

Проверьте /health/ready, число stock_movements и audit_events, а также доступные остатки. Время RTO 30 минут **не измерялось и не заявляется как достигнутое**.

## Миграции

backend/migrations/001_init.sql применяется entrypoint PostgreSQL при первом запуске с пустым томом. При повторном старте на существующем томе SQL не выполняется. Следующие миграции должны быть отдельными последовательными файлами; сброс тома не является допустимой процедурой обновления рабочей БД.

## Логи и диагностика

~~~bash
docker compose ps
docker compose logs -f api worker
docker compose exec db pg_isready -U stockpilot -d stockpilot
~~~

API ведёт JSON-строки логов с requestId, маршрутом и длительностью, экспортирует /metrics в приватной сети контейнеров. При публикации метрик требуется отдельная авторизация.


## Проверка восстановления без изменения основной БД (v0.3.0)

На отдельном локальном стенде с установленным Docker Compose:
```bash
STOCKPILOT_VERIFY_RESTORE=1 sh scripts/verify_restore.sh
```
Скрипт делает настоящую PostgreSQL-архивную копию, восстанавливает её во временную базу `stockpilot_verify_...`, сравнивает контрольные суммы журналов, количества сущностей и балансы, затем удаляет временную БД. При записи в рабочую БД во время копирования проверка намеренно не проходит. Результат выводится как JSON с `backupSeconds`, `restoreSeconds`, `totalSeconds`. Не используйте это как доказательство полного RTO production.

## Профиль одновременных чтений

На **тестовой демобазе**, предварительно наполненной `app.seed`, выполните:
```bash
docker compose exec -T -e STOCKPILOT_PERF_ALLOW=1 api python -m app.load_profile > load-report.json
```
Скрипт временно создаёт 60 отдельных учётных записей, запускает параллельно 600 авторизованных чтений каталога/остатков, измеряет p50/p95/p99 и число ошибок; тестовые пользователи удаляются после завершения. Профиль не включает дневной поток 350 заказов и 3000 движений. В CI оба отчёта сохраняются как `stockpilot-03-operational-evidence` в артефактах job compose.


## Разделение PostgreSQL-прав (v0.4.0)

В `.env` должны быть **два разных логина**: `POSTGRES_USER` владеет схемой и применяется только в `db/migrate`; `APP_DB_USER` создаётся контейнером `migrate`, и именно он используется в `DATABASE_URL` сервисов `api` и `worker`. Пароли owner и приложения должны быть разными. `APP_DB_PASSWORD` доступен только миграционному контейнеру. Никогда не храните реальные секреты в Git.

Файл [scripts/db_roles.sql](../scripts/db_roles.sql) выдаёт API минимально достаточные объектные права, исключая UPDATE/DELETE в `stock_movements` и `audit_events`; ограниченная роль не может отключать триггеры или менять DDL. Схема/миграции остаются во владении владельца PostgreSQL. Перед возвратом трафика проверьте:

```bash
docker compose ps
docker compose exec -T api python -m app.security_check
```

Проверка завершится ошибкой, если API работает от суперпользователя, умеет создавать объекты в `public` или переписывать учётные журналы.

При последующих добавлениях таблиц права на них должны явно учитываться в `scripts/db_roles.sql` (применяется при каждом старте миграционного контейнера).

### Общие лимиты запросов

Данные фиксированных 60-секундных окон теперь хранятся в `rate_limit_counters`. Максимумы: 30 входов в минуту и 2000 API-вызовов в минуту с одного подтверждённого клиентского адреса. При ошибке PostgreSQL запрос не пропускается без проверки. Worker очищает старые счётчики ограниченными пакетами. На 429 возвращается `Retry-After: 60`.

Для IP используется адрес соединения; заголовок `X-Real-IP` принимается **только** от peer-адресов, входящих в настроенные `TRUSTED_PROXY_CIDRS`. Неконтролируемый `X-Forwarded-For` игнорируется. Перед production задайте узкую доверенную сеть и ограничьте прямой доступ к API. Фиксированные окна допускают пограничный burst; для сложного публичного развертывания нужно дополнительно применять rate-limit на ingress и провести независимый security-аудит.


## Управление сотрудниками (v0.5.0)

Раздел «Администрирование» доступен только роли `admin`. Из списка сотрудников можно назначить один или несколько активных складов, заблокировать/разблокировать пользователя и создать нового сотрудника. Сервер применяет замену складских назначений в одной транзакции PostgreSQL; при ошибке или несуществующем складе ничего не изменяется. При реально изменённых правах `token_version` увеличивается, поэтому все прежние JWT сотрудника перестают работать. Выдавайте сотруднику только необходимые склады.

Блокировка выполняет `active=false` и увеличивает `token_version`. Заблокированный сотрудник не может войти; разблокировка не восстанавливает старые сеансы. Самоблокировка администратора отвергается сервером. Применяются неизменяемые события аудита `user.warehouses_change` и `user.status_change`.

В обратном прокси nginx добавлена явная передача `X-Real-IP: $remote_addr` до API. `TRUSTED_PROXY_CIDRS` должен включать адрес nginx-контейнера/защищённой внутренней сети, а не произвольный внешний адрес. Клиентский `X-Real-IP` перезаписывается nginx, его нельзя использовать как недоверенный параметр. При наличии внешнего прокси перед nginx следует отдельно настроить доверенные `set_real_ip_from`/сетевые правила; по умолчанию не следует доверять внешним forwarded-заголовкам.
