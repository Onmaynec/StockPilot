# Эксплуатация и восстановление

## Резервное копирование

~~~bash
mkdir -p backups
bash scripts/backup.sh backups/stockpilot.dump
~~~

Используется pg_dump -Fc внутри контейнера PostgreSQL. Бэкапы могут содержать персональные данные, не добавляйте их в Git. В production нужны внешнее зашифрованное хранилище, ежедневное расписание и ротация.

## Восстановление

**Осторожно: заменяет данные в целевой БД!** Перед началом создайте дополнительную копию.

~~~bash
docker compose stop api worker web
STOCKPILOT_ALLOW_DESTRUCTIVE_RESTORE=1 sh scripts/restore.sh backups/stockpilot.dump
docker compose up -d --build
docker compose exec -T api python -m app.security_check
~~~

Перед разрушительным восстановлением скрипт проверит обязательную SHA-256 sidecar, явное разрешение и отсутствие работающих `api`, `worker`, `web`. Неподписанные/повреждённые архивы не принимаются. После восстановления проверьте /health/ready, число stock_movements и audit_events, а также доступные остатки. Время RTO 30 минут **не подтверждено для production**.

## Автоматическая служба резервного копирования (v0.7.0)

Новая служба `backup` активируется отдельно через профиль Docker Compose. Она не публикует портов и подключается к PostgreSQL через внутреннюю сеть. Дамп `pg_dump -Fc` записывается во временный файл; только после успешной проверки структуры `pg_restore --list` атомарно переименовывается в `stockpilot-YYYYMMDDTHHMMSSZ-PID.dump`. Создаётся SHA-256 sidecar `<archive>.sha256`, после чего проверяется контрольная сумма. Если dump или checksum завершились с ошибкой, неполный временный архив удаляется, а существующие архивы сохраняются без изменений.

```bash
mkdir -p backups && chmod 700 backups
# Linux: пропишите в .env BACKUP_UID=$(id -u) и BACKUP_GID=$(id -g)
# Также доступны BACKUP_RETENTION_DAYS=14 и BACKUP_INTERVAL_SECONDS=86400
docker compose --profile backup up -d backup
docker compose logs -f backup
# Разовый запуск вместо автоматической службы:
docker compose run --rm backup /bin/sh /scripts/backup_rotate.sh
```

**Расписание:** первый бэкап сразу после включения сервиса; следующие через `BACKUP_INTERVAL_SECONDS` от успешной попытки (по умолчанию 24 часа), ошибки логируются и повторяются через 5 минут. Это периодический запуск, а не привязка к конкретному часу суток. При перезапуске резервное копирование производится немедленно. Архивы находятся в `./backups` на хосте, **отдельно от тома PostgreSQL**, не добавляются в Git. Срок хранения по умолчанию 14 полных суток; удаляются только архивы по маске `stockpilot-*.dump`, старше срока, с ожидаемым checksum sidecar, при этом два самых новых архива не удаляются. Защита от параллельного запуска реализована отдельным lock-каталогом `.stockpilot-backup.lock`: после аварийного завершения может потребоваться удалить устаревшую блокировку после проверки отсутствия работающего задания.

**Безопасность:** бэкап содержит полные данные и сведения о пользователях. Локальный SHA-256 не является шифрованием или защитой от умышленной подмены одновременно архива и sidecar. В production обеспечьте хостовые ACL, шифрование хранилища, отдельное зашифрованное офсайт-хранилище, мониторинг успешности задания и резервное управление ключами. В opt-in контейнере используются DB-owner credentials для полного дампа; не публикуйте его сокеты и сети. На Linux папка монтируется в контейнер и создаётся с режимом 700; на Windows проверьте реальные NTFS ACL. Контейнер запускается без root с `BACKUP_UID`/`BACKUP_GID`: для Linux укажите фактические `id -u`/`id -g` пользователя, владеющего `backups/`. Иначе сервис честно откажет в записи, а не создаст архив, который оператор потом не сможет прочитать. На Docker Desktop права и отображение UID могут отличаться — проверьте создание архива и последующий локальный `sha256sum -c` вручную.

### Полное учебное восстановление на изолированном стенде

```bash
STOCKPILOT_RECOVERY_DRILL=1 STOCKPILOT_RECOVERY_ISOLATED=1 \
  sh scripts/recovery_drill.sh backups/stockpilot-YYYYMMDDTHHMMSSZ-PID.dump
```

Скрипт требует существующий архив и корректный SHA-256 sidecar и работает через **отдельный Compose-файл `compose.recovery.yml` и отдельный project**. У recovery-стенда свои сеть, `PGDATA` и учётные роли, нет портов, опубликованных на хост. После восстановления `pg_restore` запускаются миграции, ограниченная прикладная роль, API, worker и nginx. Проверяется `app.security_check`, проксированный `/health/ready`, выдача корневой страницы и совпадение контрольных отпечатков основных документов, аудита, проводок и агрегированных физических остатков. В конце удаляются **только** тома и контейнеры временного project, основная БД не очищается.

JSON содержит `restoreSeconds` и `fullStackRecoverySeconds`, включающие восстановление и запуск приложения на данном стенде. Скрипт ожидает отсутствие бизнес-записей в основной базе после создания выбранного архива: если источник изменился, сравнение со старым архивом не подтверждает корректность новой версии данных и тест завершается отказом. Для production требуется отдельный тест на копии боевой инфраструктуры с реальными объёмами и заранее определённой точкой восстановления, включая проверку бизнес-сценариев и регламент оператора. **AT-11 RTO <30 минут на production считается открытым до такого испытания.**

Ручной `scripts/backup.sh` теперь также создаёт sidecar и не перезаписывает существующий файл. `scripts/restore.sh` требует `STOCKPILOT_ALLOW_DESTRUCTIVE_RESTORE=1`, валидный checksum и остановленные сервисы. Для восстановления старых дампов без sidecar сначала подготовьте доверенный архив и checksum в защищённой среде: не отключайте защиту ради случайного файла.

## Миграции

backend/migrations/001_init.sql применяется entrypoint PostgreSQL при первом запуске с пустым томом. При повторном старте на существующем томе SQL не выполняется. Следующие миграции должны быть отдельными последовательными файлами; сброс тома не является допустимой процедурой обновления рабочей БД.

## Логи и диагностика

~~~bash
docker compose ps
docker compose logs -f api worker
docker compose exec db pg_isready -U stockpilot -d stockpilot
~~~

API ведёт JSON-строки логов с requestId, маршрутом и длительностью, экспортирует /metrics в приватной сети контейнеров. При публикации метрик требуется отдельная авторизация.


## Проверка восстановления без изменения основной БД (v0.3.0)

На отдельном локальном стенде с установленным Docker Compose:
```bash
STOCKPILOT_VERIFY_RESTORE=1 sh scripts/verify_restore.sh
```
Скрипт делает настоящую PostgreSQL-архивную копию, восстанавливает её во временную базу `stockpilot_verify_...`, сравнивает контрольные суммы журналов, количества сущностей и балансы, затем удаляет временную БД. При записи в рабочую БД во время копирования проверка намеренно не проходит. Результат выводится как JSON с `backupSeconds`, `restoreSeconds`, `totalSeconds`. Не используйте это как доказательство полного RTO production.

## Профиль одновременных чтений

На **тестовой демобазе**, предварительно наполненной `app.seed`, выполните:
```bash
docker compose exec -T -e STOCKPILOT_PERF_ALLOW=1 api python -m app.load_profile > load-report.json
```
Скрипт временно создаёт 60 отдельных учётных записей, запускает параллельно 600 авторизованных чтений каталога/остатков, измеряет p50/p95/p99 и число ошибок; тестовые пользователи удаляются после завершения. Профиль не включает дневной поток 350 заказов и 3000 движений. В CI оба отчёта сохраняются как `stockpilot-03-operational-evidence` в артефактах job compose.


## Разделение PostgreSQL-прав (v0.4.0)

В `.env` должны быть **два разных логина**: `POSTGRES_USER` владеет схемой и применяется только в `db/migrate`; `APP_DB_USER` создаётся контейнером `migrate`, и именно он используется в `DATABASE_URL` сервисов `api` и `worker`. Пароли owner и приложения должны быть разными. `APP_DB_PASSWORD` доступен только миграционному контейнеру. Никогда не храните реальные секреты в Git.

Файл [scripts/db_roles.sql](../scripts/db_roles.sql) выдаёт API минимально достаточные объектные права, исключая UPDATE/DELETE в `stock_movements` и `audit_events`; ограниченная роль не может отключать триггеры или менять DDL. Схема/миграции остаются во владении владельца PostgreSQL. Перед возвратом трафика проверьте:

```bash
docker compose ps
docker compose exec -T api python -m app.security_check
```

Проверка завершится ошибкой, если API работает от суперпользователя, умеет создавать объекты в `public` или переписывать учётные журналы.

При последующих добавлениях таблиц права на них должны явно учитываться в `scripts/db_roles.sql` (применяется при каждом старте миграционного контейнера).

### Общие лимиты запросов

Данные фиксированных 60-секундных окон теперь хранятся в `rate_limit_counters`. Максимумы: 30 входов в минуту и 2000 API-вызовов в минуту с одного подтверждённого клиентского адреса. При ошибке PostgreSQL запрос не пропускается без проверки. Worker очищает старые счётчики ограниченными пакетами. На 429 возвращается `Retry-After: 60`.

Для IP используется адрес соединения; заголовок `X-Real-IP` принимается **только** от peer-адресов, входящих в настроенные `TRUSTED_PROXY_CIDRS`. Неконтролируемый `X-Forwarded-For` игнорируется. Перед production задайте узкую доверенную сеть и ограничьте прямой доступ к API. Фиксированные окна допускают пограничный burst; для сложного публичного развертывания нужно дополнительно применять rate-limit на ingress и провести независимый security-аудит.


## Управление сотрудниками (v0.5.0)

Раздел «Администрирование» доступен только роли `admin`. Из списка сотрудников можно назначить один или несколько активных складов, заблокировать/разблокировать пользователя и создать нового сотрудника. Сервер применяет замену складских назначений в одной транзакции PostgreSQL; при ошибке или несуществующем складе ничего не изменяется. При реально изменённых правах `token_version` увеличивается, поэтому все прежние JWT сотрудника перестают работать. Выдавайте сотруднику только необходимые склады.

Блокировка выполняет `active=false` и увеличивает `token_version`. Заблокированный сотрудник не может войти; разблокировка не восстанавливает старые сеансы. Самоблокировка администратора отвергается сервером. Применяются неизменяемые события аудита `user.warehouses_change` и `user.status_change`.

В обратном прокси nginx добавлена явная передача `X-Real-IP: $remote_addr` до API. `TRUSTED_PROXY_CIDRS` должен включать адрес nginx-контейнера/защищённой внутренней сети, а не произвольный внешний адрес. Клиентский `X-Real-IP` перезаписывается nginx, его нельзя использовать как недоверенный параметр. При наличии внешнего прокси перед nginx следует отдельно настроить доверенные `set_real_ip_from`/сетевые правила; по умолчанию не следует доверять внешним forwarded-заголовкам.

## Поисковые индексы v0.5.0

Миграция `005_catalog_search.sql` создаёт `pg_trgm` и GIN-индексы `idx_products_sku_search`, `idx_products_name_search`, `idx_products_barcode_search`. Они ускоряют частичный поиск с `ILIKE` без изменения результатов. Для тестовой базы с массовым seed после загрузки каталога полезно выполнить `ANALYZE products` под владельцем схемы. В CI этот шаг производится до измерения p50/p95. Первую миграцию большого каталога проводите в окно низкой нагрузки: `CREATE INDEX IF NOT EXISTS` без `CONCURRENTLY` может удерживать блокировки.


## Профиль конкурентной записи (v0.6.0)

На **выделенном уничтожаемом** стенде с `app.seed` и ровно 12 000 исходных seed-проводок можно запустить:

```bash
docker compose exec -T -e STOCKPILOT_WRITE_PROFILE_ALLOW=1 -e STOCKPILOT_WRITE_PROFILE_ISOLATED=1 -e STOCKPILOT_WRITE_TRANSFERS=20 api python -m app.write_profile
```

Это НЕ read-only испытание. Процедура через HTTP API создаёт новый тестовый SKU, новую ячейку, партию, приёмку 8 единиц, 20 заказов и конкурентно пытается зарезервировать по 1 единице: должно быть ровно 8 подтверждений и 12 предсказуемых ошибок INSUFFICIENT_STOCK. Далее она проводит 20 двухстрочных перемещений исходного seed-SKU между ячейками. Контроль читает из PostgreSQL суммарные балансы, число строк журнала и отсутствие чистого изменения количества после перемещений. JSON содержит p95 создания заказа/проведения приёмки/резерва/перемещения. Исходные записи сохраняются как история демобазы.

**Запрещено выполнять на production** даже с отдельным разрешением: скрипт предназначен только для одноразовой изолированной базы и проверяет точный seed. Для более длинного испытания на отдельном тестовом стенде переменная `STOCKPILOT_WRITE_TRANSFERS` допускает значения 1–1500, но квота HTTP 2000 запросов/мин и аппаратные параметры могут потребовать отдельного распределённого генератора нагрузки. Полная смешанная приёмка AT-10 не завершена.

## Мобильная комплектация и назначения (v0.8.0)

Откройте **Задания отбора** с ролью `supervisor` или `admin`. Для задания со статусом `pending` выберите исполнителя из списка доступных кладовщиков: в списке только активные сотрудники, назначенные на выбранный склад. Запрос `GET /api/v1/picks/assignees` проверяет права на складе и не возвращает чужих сотрудников. Для оператора с ролью `picker` выберите «Мои активные задания»: API получает только задачи с `assigned_to = current user`.

Для каждого задания сверьте SKU/штрихкод с товаром и фактическое количество. Нельзя ввести дробное количество или больше резерва. Если фактически отобрано меньше ожидаемого, интерфейс предупреждает об ожидающем согласования недоборе. Только `supervisor`/`admin` могут его утвердить; серверные проверки сохраняются независимо от интерфейса. Если камера недоступна, используйте текстовое поле без попыток отправки данных при отсутствии связи.

На общем терминале обязательно нажимайте **Выйти** после работы: при выходе удаляются сеансовые черновики. Они не хранятся в постоянном локальном хранилище браузера. После обновления со старых версий устаревшие черновики удаляются при первом открытии приложения.

Физическая проверка AT-12 перед производственным использованием: экран шириной 375 px, Android Chrome и Windows Edge, разрешение/запрет камеры, внешний сканер как клавиатура, потеря связи перед отправкой, возврат после смены исполнителя, корректное завершение роли на общем устройстве. Автоматическая проверка не заменяет этот протокол.


## Смешанный профиль производительности AT-10 (v0.9.0)

**Запускайте только на отдельной одноразовой демобазе. Не запускайте write-профиль на рабочем складе:** он создаёт 350 заказов, 1 500 документов перемещения, 3 000 проводок, контрольные товары/приёмки и 60 временных сотрудников. После выполнения сотрудники деактивируются и их токены отзываются; тестовые документы, проводки и аудит намеренно остаются в БД. Для очистки используйте только уничтожение отдельной тестовой БД после сохранения отчёта.

Демобаза должна содержать ровно 12 000 исходных seed-движений (python -m app.seed). Write-профиль намеренно принимает только URL loopback 127.0.0.1 и требует, чтобы в окружении API было явно разрешено доверие 127.0.0.1/32: это позволяет каждому тестовому сотруднику использовать отдельный синтетический адрес X-Real-IP, не расширяя доверие к сетевым клиентам. Не переносите эту настройку в production и не доверяйте произвольным заголовкам на публичном ingress.

На одноразовом стенде временно установите в .env:

~~~dotenv
TRUSTED_PROXY_CIDRS=127.0.0.1/32
~~~

Пересоздайте только тестовый API, затем запустите профили:

~~~bash
docker compose up -d --force-recreate api
docker compose exec -T -e STOCKPILOT_PERF_ALLOW=1 -e STOCKPILOT_LOAD_P95_LIMIT_MS=500 api python -m app.load_profile
docker compose exec -T \
  -e STOCKPILOT_WRITE_PROFILE_ALLOW=1 \
  -e STOCKPILOT_WRITE_PROFILE_ISOLATED=1 \
  -e STOCKPILOT_WRITE_URL=http://127.0.0.1:8000/api/v1 \
  -e STOCKPILOT_WRITE_ORDERS=350 \
  -e STOCKPILOT_WRITE_TRANSFERS=1500 \
  -e STOCKPILOT_WRITE_P95_LIMIT_MS=1500 \
  api python -m app.write_profile
~~~

Read-профиль создаёт 60 временных менеджеров, запускает 600 авторизованных запросов каталога и остатков и удаляет этих пользователей. Write-профиль создаёт 30 менеджеров и 30 кладовщиков, одновременно начинает 30 заказов и 30 проведений перемещения, затем завершает 350 заказов, резервирует 20 из них против восьми единиц и проводит 1 500 обратимых перемещений. Итоговая проверка сверяет 3 000 неизменяемых ledger-записей, нулевое сальдо перемещений и физические остатки в обеих ячейках.

Цели CI: p95 чтения каталога/остатков ≤500 мс; p95 создания/проведения документов ≤1 500 мс. Отчёты содержат p50/p95/p99, ошибки, версии Python/PostgreSQL, основные параметры PostgreSQL и best-effort метрики cgroup CPU/RAM. Если cgroup не предоставляет отдельные поля, в JSON они остаются null; значение не подменяется оценкой.

После теста верните TRUSTED_PROXY_CIDRS к узкому диапазону реального доверенного ingress и пересоздайте API. Результаты CI на демонстрационном хосте подтверждают только фиксированный AT-10 профиль, а не 24-часовую production-эксплуатацию.
